# 💬 jschat.xcf.ai

JavaScript port of **xcf-chat** (Swift `ChatServer` + `MultiPeerChatCore` + `DogTagKit`) for **Cloudflare Workers**.
It covers the same HTTP routes, the WebSocket chat protocol and the WebAuthn/passkey API, and it serves the same browser front-end.

## Swift → JS map

| Swift (xcf-chat-main/Sources) | JS (src/) | Runs on |
|---|---|---|
| `ChatServer/main.swift` (`--rp-id`, `--admin`) | `index.js` + `wrangler.jsonc` vars `RP_ID`, `ADMIN_USERNAME` | Worker |
| `StaticContentProvider.swift` + `static/` | `public/` (Workers Static Assets) | Worker |
| `WebServer.swift` (router, admin API, uploads, icons, WebSocket) | `chat-server.js` | Durable Object |
| `WebChatServer.swift` (rooms, messages, invites, emojis) | `chat-server.js` | Durable Object |
| `Models.swift` | `models.js` | |
| `PersistenceManager.swift` (UserDefaults) + SwiftData store | `persistence.js` (Durable Object SQLite) | |
| `FileManager.swift` (uploads dir) | `file-manager.js` (R2 bucket) | |
| `AdminManager.swift`, `WebAuthAdminManager.swift` | `admin-manager.js` | |
| `WebAdminContent.swift` | `admin-content.js` (generated by `npm run extract-admin`) | |
| `DogTagKit/WebAuthnServer.swift` | `webauthn/server.js` | |
| `DogTagKit/WebAuthnManager.swift` (CBOR, ES256/RS256/U2F, sign counts) | `webauthn/manager.js`, `webauthn/cbor.js` | |
| `DogTagKit/WebAuthnTypes.swift` | `webauthn/types.js` | |
| CoreGraphics icon/preview generators | `icons.js` | |

There is one global `ChatServer` Durable Object, so like the Swift process it is the single owner of all chat state.

## Passkeys
All the WebAuthn endpoints are ported:
- **Registration:** `/webauthn/register/begin` (plus `/linux`, `/linux-software`, `/universal`, `/hybrid` and `/android`) and `/webauthn/register/complete`.
- **Authentication:** `/webauthn/authenticate/begin` (plus `/linux-software` and `/hybrid`) and `/webauthn/authenticate/complete`.
- **Username check:** `/webauthn/username/check`.

Signature verification uses WebCrypto (ECDSA P-256 and RSASSA-PKCS1-v1_5) instead of CryptoKit/Security.framework.

**`RP_ID` must equal the hostname users open**, which is `jschat.xcf.ai` in production. Passkeys created on `chat.xcf.ai` belong to that domain and can't be reused here, so users register again.

## Run locally
```sh
npm install
npm run dev        # http://localhost:8787 with RP_ID=localhost
npm test           # WebAuthn unit tests (software passkey authenticator)
npm run e2e        # end-to-end checks against the dev server
```

## Deploy
```sh
npx wrangler login
npx wrangler r2 bucket create jschat-uploads
npm run deploy     # creates the jschat.xcf.ai custom domain (xcf.ai must be a zone on your account)
```
Then go to `https://jschat.xcf.ai` and register a passkey with the username set in `ADMIN_USERNAME` (default **XCF Admin**). That account is promoted to admin automatically. The admin panel is at `/admin`.

## Differences forced by the platform
- **Emoji colours (`/emoji/analyze`):** the Swift server drew the emoji with CoreText. Workers can't render fonts, so the port averages the fill colours of the matching Twemoji SVG instead. The contrast and text-colour math is the same.
- **Thumbnails:** the Swift server made thumbnails with AppKit/UIKit. Workers can't, so `thumbnailPath` is `null`, which is what the Swift build does on platforms without those frameworks. Clients show the original image instead.
- **Admin sessions:** these are also saved in Durable Object storage, so they survive the object being evicted from memory. Expiry is still 1 hour. Expired sessions are cleaned up on each request instead of on a 15-minute timer.
- **Storage:** SwiftData and UserDefaults are replaced by Durable Object SQLite, and the `~/Documents/uploads` folder is replaced by R2.

## Swift behaviours kept as-is (they might be worth fixing later)
- **No challenge or `rpIdHash` check:** `verifyClientData` checks only the `type` and origin of `clientDataJSON`. It doesn't compare the challenge with the one it issued, and it doesn't check the `rpIdHash` in `authenticatorData`.
- **Admin API access is too broad:** `hasValidAdminSession` lets anyone call the admin API while *any* admin session is active.
- **Room participant count only grows:** a `Room`'s `participantCount` goes up on every join because `User` gets a new id each time.
- **Invite links point nowhere:** they use `http://<rpId>/join/<code>`, and no route serves `/join/`.
